# mechababs — study-first requirements spec

The decisions of record for the study-first implementation.
[use_cases.md](use_cases.md) holds the user stories these answer to; [output_structure.md](output_structure.md) holds the resulting layout; this document holds the requirements and the reasoning behind them.
Each entry should trace to a use case.

The spec is a contract for implementation, not gospel: it was written before contact with the real code.
If a requirement forces the implementation somewhere weird, inefficient, or sloppy, the requirement is revisited — loudly, with options — rather than followed blindly.
Entries marked **Open** are named holes we have not decided.

## Installer & environment

- **No global install; no separate bootstrap verb.** The first command is `uvx mechababs campaign init …` — run ephemerally via uvx (nothing on PATH), it creates the first campaign *and* installs the venv. There is no standalone `bootstrap` step.
- **`campaign init --superstudy <name>` scaffolds a new superstudy** and creates the campaign at that level.
- **Init is scaffold-or-adopt, and never clobbers.** Three cases, decided by what is already at the target path. *Nothing there* → create the datalad dataset, then scaffold `.mechababs/` and the campaign inside it. *Already a datalad dataset* → scaffold `.mechababs/` at its root; the directory may already carry campaigns, and an existing one is never modified. *A campaign with this label already exists* → refuse, naming it. So a superstudy that has run campaigns before gains another by the same command that creates one from scratch, and adopting an existing dataset is the normal path rather than a special mode — the same rule at either level.
- **`campaign init` names its target with `-d`, mirroring datalad; every other verb runs from the root of the correct dataset.** `campaign init -d .` or `-d <path>` says which dataset to create the campaign in, the way `datalad -d` does, so the one verb that has to act on a dataset you may not be standing in says so explicitly. `--superstudy <name>` is the superstudy's counterpart and names the superstudy itself — created if that name is not there yet, adopted if it is. The superstudy is **not** the campaign and outlives it: one superstudy accumulates many campaigns over time, each its own label and config epoch, so the two are named separately and neither is derivable from the other. The operating verbs (`add-dataset`, `iterate`, `status`, `retire-derivative`) take no such flag: they run from the root of the dataset that owns the campaign — the superstudy for a super-configured campaign, the study for a study-configured one. That is what makes "operate a campaign only from the level it was configured" checkable rather than conventional, and it is why a superstudy-level `add-dataset` reaches a member with a `--study` selector instead of a different place to stand.
- **The uvx source can be a git ref or (future) PyPI.** This implementation uses a git ref (`uvx --from git+…@<ref> mechababs campaign init …`); a PyPI release gives the cleaner `uvx mechababs campaign init …` later. Publishing to PyPI is out of scope here (tracked by con/mechababs#113), but the design must not preclude it.
- **Once a campaign exists, mechababs runs from the installed venv** — uvx is only the first-campaign step; subsequent `campaign init` / `iterate` / … run from the venv.
- **One venv per campaign.** A campaign is one config epoch = one lock = one venv, pinning `mechababs` *and* `babs` together. The campaign is selected by label, so the CLI resolves the venv — the user never passes a project path.
- **Activate from the top level, then work.** The user activates the campaign's venv from the **superstudy if one exists, else the study**, and works from there. For a super-configured campaign, a member study carries no operational venv — one can be rebuilt from the member's committed lock for detached use, but `iterate` there still refuses without `--force`. A member may also define study-level campaigns of its own (distinct labels; venv at the study, normal lone-study rules), but a member's own campaign and a super-campaign covering that member are **not run at the same time** — the member directory is shared state. The venvs themselves are gitignored and ephemeral, so nothing committed conflicts.
- **Each study carries the campaign lock (`.mechababs/campaigns/<label>/uv.lock`), committed — the study's own orchestration-provenance record, not a dormant copy.** All orchestration provenance lives in the study, so the study is independently reproducible: `uv sync` the lock, `datalad rerun` the recorded commands. The operational venv lives at the configured level (super for a super-campaign, study for a study-campaign) — one active venv per campaign; the venv is gitignored, rebuilt from the lock.
- **The lock is mutable via git history — this is how a mid-sweep version bump works.** A bump edits and commits the lock (a new study commit); completed cells keep the commit/lock that produced them (never redone), while new and selectively-redone cells run at the bumped lock. The lock's evolution *is* its git history: a `datalad rerun` checks out the run's commit → `uv sync` that commit's lock → rebuilds the exact env → redoes. The campaign goes deliberately heterogeneous (some cells at the old version, some at the new), honestly recorded. At a superstudy the bump edits the **canonical lock at the super**; members receive it via `iterate`'s ensure step (see the canonical-vs-mirror entry below), never by hand-editing a member's copy.
- **The cluster config may declare `env_constraints`, and `campaign init` folds them into the campaign's pyproject.** Which package versions a site can install is a cluster fact, not a campaign or app one: an old glibc (CentOS 7's 2.17 is still common on HPC) stops loading the newest manylinux wheels long before it stops running jobs, and uv then falls back to source builds the site's compiler cannot complete. So a cluster config carries a list of verbatim PEP 508 specifiers, emitted as uv `constraint-dependencies` — caps that apply to whatever the resolution already contains, never adding a dependency or pinning one the site does not use. mechababs does not interpret them; the semantics are uv's. Absent or empty means no constraints, so a modern cluster declares nothing. When the environment build still hits a package with no installable wheel, `campaign init` fails naming that package and pointing at `env_constraints`, rather than leaving a compiler error to be read.
- **The env-match guard checks the venv against the current committed lock.** Before mechababs operates, the running venv must match the campaign's committed lock — refuse on mismatch (bumped the lock but didn't rebuild the venv, or vice versa).
- **Honest caveat:** standalone reproduction is faithful only for fully-pinned locks (release- or commit-pinned deps are content-fixed and rebuild identically); a dev/editable/branch source does not reproduce — the accepted cost of one-tool-two-modes.

## Layout & input

- **Input is an existing BIDS study.** mechababs operates on a study that already exists on disk (cloned, or authored by another tool); it does not create one in this implementation. Not ruled out later — see the study-authoring gap in [output_structure.md](output_structure.md).
- **The expected study input includes the per-subject metadata TSV** (per-subject `datatypes` / `t1w_num` / `bold_num`) that selection and the `add-dataset` sniff read to apply eligibility rules. For this implementation it is expected present, as OpenNeuroStudies provides. Generating it when absent is follow-up generalization work. Eligibility rules are unchanged.
- **The container dataset is an input, not something mechababs vendors.** An app config's `container.source` is handed to `babs init --container-ds` as-is when it is a URL (what a production config carries), and otherwise resolved as a filesystem path — a relative one against the **study root**, so a config can name a sibling checkout without committing an absolute path. There is no copy-into-the-campaign step: babs installs the container dataset into each derivative, the way it installs any input. This works against a container dataset in its own native layout (ReproNim/containers' `images/<collection>/<app>--<version>.sif`) because babs resolves the image from its datalad-containers registration rather than a fixed path — `PennLINC/babs#399`, which is why the pinned babs matters here.
- **Derivative naming carries the source-dataset id when the sourcedata is named.** A cell is (source dataset × app config), and `<Tool>-<Ver>+<stage>` alone would collide when a study holds several source datasets. When the sourcedata uses a generic slot (`sourcedata/raw`, `sourcedata/rawbids`) no id is needed; otherwise the derivative is `<Tool>-<Ver>+<stage>+<id>/` (e.g. `fMRIPrep-25.1.1+anat+ds000001`).

## Campaign definition

- **Campaign selection: always the env var.** The `MECHABABS_CAMPAIGN` env var names the `<label>`, and sourcing the campaign's `env.sh` is what sets it — no default-if-one shortcut, so one campaign and five behave identically. No `--campaign` flag in this implementation (not ruled out later). The `<label>` (the `.mechababs/campaigns/<label>/` dir name) is the identity; the env var is a selector, not identity; there is no stored "active" pointer.
- **`campaign init` scaffolds a per-campaign `env.sh`.** Sourcing it both activates that campaign's venv and exports `MECHABABS_CAMPAIGN=<label>` — one step that selects and activates, and (because there is one venv per campaign) the two cannot mismatch. A user-sourced script works where an auto-set env var would not: it sets the current shell, whereas a mechababs subprocess cannot export to its parent. `env.sh` is committed (the venv path is deterministic) and lives where the venv does — the superstudy if one exists, else the study. The env-match guard still backstops a hand-set `MECHABABS_CAMPAIGN` whose venv isn't active.
- **App configs are user-provided.** mechababs ships `examples/` as starters to copy and adapt — not an authoritative shipped library. The configs a campaign runs are the user's own; the ease story is reuse of those configs.
- **Cluster configs are user-provided too** — same rule. Cluster configs are site-specific and often private (real paths never belong in `examples/`); mechababs ships example clusters as starters only.
- **`campaign init` locates configs by path or URL** — app and cluster configs are given as paths or URLs and copied into `.mechababs/campaigns/<label>/` (`bids-app-configs/`, `clusters/`). Not bare names resolved against a magic directory.
- **Which source datasets a campaign acts on is an explicit selection, via a required `add-dataset` step — not at `campaign init`.** A study may hold many source datasets and a campaign may act on only some. `campaign init` defines the app bundle + cluster + env; `add-dataset` then selects which source datasets the campaign acts on, populating the cells. The statefile cells are (selected source datasets × apps).
- **At a superstudy, a member's campaign footprint is written at `add-dataset`, not `campaign init`.** `campaign init` at a superstudy touches only the superstudy's own campaign dir — no members are selected yet, so there is nothing to fan out to. When `add-dataset` first selects a source dataset in a member, it writes that member's `.mechababs/campaigns/<label>/` (config copy, lock, empty statefile shard, superstudy-mode marker). A member added later gets its footprint the same way — the copy happens at selection time, so there is no separate catch-up step.
- **`depends_on` is a mechababs-owned declaration in the app config, separate from babs's input config.** Each bids-app config names its own `depends_on` (e.g. fmriprep-minimal → fmriprep-anat). It is **not** derived from babs's `input_datasets` — orchestration topology is mechababs's, run-wiring is babs's; coupling them would also miss dependencies that are never inputs (a QC gate). A "pipeline" is the connected component of the edge graph — a derived view, not a stored object. The design leaves room for a first-class pipeline/bundle object that owns the topology later, without reworking the config format.
- **`depends_on` carries no kind: it is ordering, and nothing else.** A bare producer stem, meaning exactly one thing — the dependent cell is not scaffolded until that producer's cell is merged. It wires nothing and mechababs reads nothing else off it.
  - **Wiring is `input_datasets`', solely.** Scaffold resolves an `input_datasets` entry that names a producer cell in the shard to that cell's merged output store, without consulting `depends_on` at all. A key naming no cell is an input from outside the campaign and keeps the `origin_url` the config gives it.
  - **The two are declared side by side, and that is deliberate.** An input-chained stage (fmriprep-minimal ← fmriprep-anat) names its producer twice — `depends_on` for ordering, `input_datasets` for wiring — because they answer different questions and are consumed by different tools. A QC gate (fmriprep ← mriqc) names it once, in `depends_on`: the producer must complete and its report matters, but its output is not an input.
  - **The gate does not act on the QC verdict.** It delays the dependent until the producer is merged; whether subjects passed, and subtracting failures from the downstream selection, stays the user's act (curating the selection), not a mechababs mechanism.
- **A config edit mid-campaign reaches only cells not yet `babs init`-ed.** App and cluster configs are mutable the way the lock is — edit and commit, with evolution read from git history (at a superstudy: edit the canonical copy at the super; members receive it via the ensure step). A cell already scaffolded keeps its baked job scripts and is not rewritten; to apply the change there, retire + re-scaffold. Awkward but honest — the same babs-bakes-at-init asymmetry as today's interventions.

## Statefile & reconciler

- **The statefile is per-(study, campaign), tall, at `.mechababs/campaigns/<label>/sourcedata+derivatives.tsv`.** One row per (source dataset × app config) cell — a map of source datasets to derivatives, named after OpenNeuroStudies' `studies+derivatives.tsv` one level down. A BIDS-conventional TSV so other tools can read it.
- **Columns:**
  - identity (inputs, written at `add-dataset`, never overwritten): `source_dataset`, `app_config`, `processing_level` (sub vs sub+ses), `n_subjects` / `n_sessions`.
    `app_config` is the **campaign-relative config path** (`bids-app-configs/MRIQC-24.0.2.yaml`), the same identity `campaign.yaml`'s `apps:` list carries; the filename stem is only a derived, human-facing form (display, derivative naming). Internal — the user names configs only at `campaign init`, by full path or URL.
    `depends_on` is *declared* in an app config by the producer's stem (the natural name to write) and stored resolved to the producer's path, so both identity columns hold the same kind of thing.
    `source_dataset` is the sourcedata's **study-relative path** (`sourcedata/ds000001`), not a bare id: it is what the user named, it is what scaffold wires into babs, and it does not assume the sourcedata sits at `sourcedata/<id>`.
    When a derivative carries an `+<id>` suffix, the id is that path's last component — and the generic slots (`sourcedata/raw`, `sourcedata/rawbids`) carry none, per the naming rule in "Layout & input".
    `processing_level` is read from the metadata rows themselves — session-level exactly when they name real sessions — rather than from which of the two metadata filenames the study happens to use.
    `n_sessions` counts sessions across all subjects, and is blank rather than 0 for a subject-level dataset.
  - topology (derived from the app config): `depends_on` (the upstream `app_config`, or empty).
  - durable derived (reconciled each tick): `babs` (the derivative path once scaffolded — empty = not started), `merged` (set once merged — empty = not yet).
  - State is read off these — `babs` empty → scaffold; `babs` set + `merged` empty → active; `merged` set → done. Volatile job status stays in babs (queried live), never a column.
- **The `depends_on` gate is a shard-local row lookup.** A cell with a `depends_on` is not scaffolded until its **producer cell is `merged`**, where the producer is the same `source_dataset`'s upstream-`app_config` row in the same shard. It cannot cross studies — not by an enforced check, but because the reconciler only ever looks within the shard it is reconciling. Same at both levels. Input wiring is a separate lookup on the same shard, driven by `input_datasets` (above).
- **The inclusion pin and `--limit` live in the campaign.** `--limit` (still needed for testing) is a `campaign init` option recorded in `campaign.yaml` — a campaign-level fact, canonical at the configured level and reaching members like the rest of the config. The requested subject list is pinned in the member's campaign footprint at `.mechababs/campaigns/<label>/inclusions/<sourcedata>_<app>.csv`, beside the statefile shard. Both halves of a cell's identity are paths, so neither is filename-safe as written: `<sourcedata>` is the whole study-relative path with `/` mapped to `-` (whole, so two source datasets whose directories share a basename cannot collide on one pin), and `<app>` is the config's filename stem. The name is constructed from the cell and never parsed back into one — written at scaffold time inside that cell's `datalad run`, so the pin (and its diff against babs's own `processing_inclusion.csv`, the check that catches a selected subject the data doesn't have) travels with the study. If a file already exists at the pin path when a cell scaffolds, it is used as-is and selection is skipped entirely — so hand-writing a one-row file there before the first tick runs a one-subject smoke test of the full pipeline, the same affordance today's campaigns have.
- **`iterate` gates by noting, not blocking.** A dependent cell whose producer is not complete is not advanced, but this is not a halt: iterate records "waiting on producer" as the cell's visible state and moves on; the next tick re-checks (level-triggered).
- **Change-making transitions are `datalad run`-captured action subcommands, not plain saves.** Each transition becomes a mechababs action verb; the ones that make changes are dispatched via `datalad run`, so the commit records the actual command verbatim instead of a hand-written save label. Only mutating actions are wrapped — a read-only or non-committing action (a status query; a submit that only sbatches and changes nothing tracked) needs no `datalad run`. This is mostly moving existing transition code into subcommands, not a rewrite.
  - **One change-making write stays outside `datalad run`: the superstudy's own campaign files.** The inner run is always dispatched at the study (`-d <study>`), so the super's membership catalog + coarse lifecycle updates cannot land inside it; they are committed at the super as plain saves.
  - `iterate` itself is a plain coordinator, **not** wrapped in a `datalad run` — it dispatches one run per advancing cell, so there is no same-level nesting.
  - The run is at the **study level** (`-d <study>`), where the derivative and statefile live. At a superstudy, `iterate` dispatches per-member study-level runs — the run's `-d` is always the (lone or member) study.
  - **Mechanics:** the inner run is `datalad run --explicit -d .` with cwd inside the study. The cwd makes the recorded command study-relative (portable, re-executable records); `--explicit` with each verb's declared output paths (the derivative, the statefile, the inclusion pin) keeps the run from deep-walking `sourcedata/raw` — datalad's dirty gate and save discovery ignore all submodule-ignore config, so path scoping is the only route. Because `--explicit` captures only declared outputs, a **once-per-tick shallow clean check** at the operating level (gitlink compare, no descent into submodule worktrees) is the loud backstop for stray side-writes; once-per-tick is deliberate (a ref-read per member submodule is fine per tick, not per cell).
  - **The scaffold verb declares `.gitmodules` among its outputs.** Registering the new derivative commits the registration mid-command, and datalad's undeclared-committed-path guard (`datalad.run.dirty-committed=error`) would refuse the run; declaring `.gitmodules` satisfies the guard while keeping it armed for genuinely unexpected mid-command commits — chosen deliberately over muting it.
- **Two record homes: orchestration → study, compute → derivative.** `datalad run -d <study> <action>` records the **orchestration** in the study (the derivative is an *output subdataset* of that run — the study-level diff is "new/updated subdataset + statefile"). `datalad run -d <derivative> singularity …` (the babs job) records the **compute** in the derivative. Different `-d`, different dataset levels, no nesting conflict.
- **Ordering is unchanged — no priority mechanism in this implementation.** Advance in default order (at a superstudy, members in catalog order; within a shard, cells in row order), bounded by `--batch`, with `depends_on` the only hard constraint. The overrides are `iterate --study` (concentrate on one member) and `--derivative` (narrow further, to one app's cells).
- **The single-writer unit is the campaign, not the study.** Within a campaign: single writer (the per-campaign flock). Concurrent campaigns in one study run **on separate branches, each in its own worktree — never the same checkout** (a shared checkout would put one campaign's in-flight changes inside the other's `datalad run` captures), with results merged afterward.
  - **Merge-back is a results-consolidation, not a relocation of running machinery.** A campaign lives its whole operating life in its worktree (where the baked store paths are valid); the branch merges back only when the campaign — or the cells being consolidated — is finished, and the merged-back derivative's RIA machinery is dead on arrival, accepted exactly as in the multi-cluster merge. Never continue operating a campaign from the merged-back copy; a cell that needs redoing after consolidation is retire + re-scaffold under a live campaign.
- **Concurrent operation *within* a single campaign is deferred** (branch-per-execution + merge). The blocker is babs's non-relocatable RIA stores (below).
- **Multi-cluster = two same-config campaigns, results merged by hand.** No single campaign spans clusters; you run one campaign per cluster (same configs) and consolidate the outputs later, conflicts hand-resolved. This works because you consolidate **results** (the derivative data — portable in git/annex), not running machinery; the babs RIA going dead on the merge is acceptable (you don't re-run a consolidated result). mechababs builds no cross-cluster coordination in this implementation.
- **Caveat, upstream: babs project non-relocatability is the local-abspath RIA stores — treat it as a babs limitation, not a permanent mechababs assumption.** babs bakes absolute local RIA paths at init, so a project can't move. This is behind: the within-campaign concurrency deferral, `retire-derivative` producing a dead archive, and the multi-cluster / branch merge killing the RIA. It is likely to change — RIAs able to live on remotes, or replaced by remotes generally — and when it does, branch-per-execution, clean relocation, and cross-cluster stop paying the abspath tax. Don't over-design around today's local RIAs.
- **The "active" cell decision is unchanged from today's model.** For a cell with `babs` set and `merged` empty, read `babs status` counts and decide: not-all-submitted → submit; still in flight → skip; all ended in failure → flag (don't merge, stop); all done → merge.
- **A dangling `depends_on` fails at `add-dataset`.** When a dependent cell is added, `add-dataset` checks the producer cell is present in the shard and fails if absent — so the producer is added first. No auto-adding the producer chain; fail early instead. Should a shard nonetheless carry one (only reachable by hand-editing), the reconciler routes that cell as waiting — naming the missing producer — and advances the others rather than failing the tick; scaffold still refuses the cell if something dispatches it anyway.
- **The super's campaign dir is canonical; member footprints are mirrors that `iterate` ensures before acting.** At a super, a tick reads the canonical config/lock at the super and, for each member it is about to advance, first syncs that member's `.mechababs/campaigns/<label>/` copy to match (ensure), then dispatches the study-level run — and the inner verb reads the **study's** copy, so the recorded run reads only in-study state and the study alone suffices for reproduction. A version bump is therefore an edit+commit at the super (plus `campaign update-env`); propagation is **lazy and level-triggered** — a non-complete member is brought to canonical when next touched, always before anything runs in it, so nothing ever acts on a stale mirror (an untouched member's mirror may lag between ticks). Complete members are never advanced, so never rewritten — they keep the config/lock that finished them. The env-match guard compares the venv to the super's canonical lock; member locks are provenance mirrors, not operational.
  - Faithful replay of a recorded run is the rewind discipline: rewind to the run's commit, rebuild the env from that commit's lock (`campaign update-env` at that checkout), then `datalad rerun --explicit` — rerun does not inherit the recorded run's explicit mode, though the recorded outputs are forwarded. A bare `datalad rerun` onto current HEAD reads today's config/lock, and the cell-state self-guard refuses the already-done cell — the desired loud failure. Caveat: `rerun --onto`/`--branch` are refused on git-annex adjusted branches, so on crippled filesystems campaigns *run* fine but the rewind-replay mechanic is unavailable; the replay route there is open.
  - **Open:** how the ensure-write is recorded in the member — its own sync verb under `datalad run` (firing only when there is a diff), vs a plain save.
  - **Open:** a mirror merely *behind* vs *diverged* (local commits in the member's campaign dir, e.g. `--force` detached work): behind → ensure updates it; diverged → flag and skip the member, never silently overwrite. To confirm.
- **The statefile always lives at a study; the superstudy has none.** A member study's campaign dir carries the `sourcedata+derivatives.tsv` (and a config copy); the superstudy's same-labeled campaign dir carries membership and no cell state. Identical for study-only (the one shard) and superstudy (N shards + rollup).
- **The superstudy commits membership + a coarse per-member lifecycle status; detailed per-cell state stays computed.** The split is by granularity and change-rate:
  - the committed catalog points to member studies and their statefiles, and carries a coarse per-member lifecycle (`pending` / `active` / `complete`), updated by `iterate` only at **material transitions** (a member starts; a member's last cell merges) — rare, roughly once per member, never per tick.
  - detailed per-cell state is computed on demand from the member shards (small git-tracked TSVs, cheaply fetchable even when derivative *content* isn't installed). It is not committed at the superstudy.
  - Store the coarse canonical thing (per-member lifecycle); compute the detailed view (per-cell from shards).
  - Drift-safe because a super-campaign is operated only from the super (the configured-level rule): only the super updates its catalog — one writer, no standalone member action can stale it.
  - **Open (noted gap, no machinery planned):** a crash between a member's terminal merge commit and the catalog write, followed by the user uninstalling the member before another tick, leaves the coarse status stale at `active` with nothing installed to heal from. The suspected answer is documentation, not machinery: check a study is no longer active before removing it.
- **`iterate` handles a study that has left the cluster by leaving it alone.** iterate advances only **installed** members; a finished study the user pushed and uninstalled is not present, so iterate skips it and never reinstalls to advance it. A done study whose content was dropped but whose git remains: iterate reads its shard → all `merged` → skip (done cells need no content). No "done" marker is needed — reinstall it later and the shard drives it (state derived from ground truth). The user's uninstall is the level-triggered signal.
- **Superstudy observability.** The coarse per-member lifecycle lives in the committed catalog, written at the material transition — it exists for off-cluster/git readers and is decoupled from `status`. `status` at the super is the computed rollup from member shards, plus installed-vs-not from local git; installed members drill into per-cell detail from their local shards, and an uninstalled member's per-cell detail requires fetching its shard (git, cheap, no content).
- **A campaign is operated only from the level it was configured.** A super-configured campaign is operated from the superstudy (optionally scoped to one member); a study-configured campaign is operated from the study. The same campaign is never operated cross-level. This gives each campaign exactly one operating level and eliminates the drift cross-level operation would cause: config copies edited in one member diverging from siblings; a tool bumped in one member so "one config epoch" erodes; a member's standalone `add-dataset` creating a cell the super's catalog doesn't list; super and member advancing the same member concurrently; two levels both claiming to drive the same label. Version bumps for a super-campaign therefore happen at the super, applied uniformly — never from inside a member. (Benign gitlink drift — a member advances, the super's pinned pointer lags — remains, reconciled at publish.)
  - **Open disagreement to resolve:** the alternative model — after a campaign is configured at the super, a member operates *independently* on that super-campaign and the super *reconciles later*. This spec rejects it because reconciling arbitrary member divergence (config/env edits made standalone) is drift we can't bound; what the design offers instead — a member running its own study-level campaigns under distinct labels — is a different affordance, not a substitute. To be discussed.
  - **Open, related:** whether the coarse committed lifecycle satisfies the dashboard want for materialized state at the superstudy, or more must be committed. To be discussed.

## CLI surface

- **Two entrypoints (console_scripts).** `mechababs` is the user CLI (`campaign init`, `add-dataset`, `iterate`, `status`, `retire-derivative`, `campaign update-env`, `test-cluster`); `mechababs-inner` (working name) carries the action verbs (`scaffold` / `submit` / `merge`) that `iterate` dispatches — the change-making ones under `datalad run`. The inner verbs are hidden from users, self-labeling in run records (a runcmd is unambiguously a machine-dispatched provenance step), and self-guarding (refuse a cell not in the right state).
- **`test-cluster` recreates the environment it was called from, in a throwaway study.** The durable pieces (per con/mechababs#104) survive study-first: the command surface, the e2e suite shipped as package data (`importlib.resources`, chosen in con/mechababs#98 precisely because under study-first there is no clone to reach into), fail-loud fixtures, and the throwaway-workspace principle. What changes is that there is no campaign to invoke it from: a campaign lives *inside* a study, so nothing standalone can be pointed at or stood in. It therefore runs from anywhere, taking a cluster config by path and a `--scratch-path` to work in — required, since there is no campaign to derive one from and RIA stores must not land in home or `/tmp`.
  - **The two pins reach the fixture campaign differently, and the asymmetry is intended.** *mechababs mirrors the caller*: with `--mechababs` unset, `campaign init` pins whichever mechababs is running it (PEP 610 install metadata), so the code validated is the code invoked — dev-exercises-prod, by the same path a user's own `campaign init` takes. *babs cannot mirror the caller*: babs is not a mechababs dependency, it is a dependency of the **generated campaign**, frozen by that campaign's lock — so the fixture campaign gets what a user's campaign would get. Both are overridable (`--mechababs URL@REF`, `--babs URL@REF`), which is how a branch gets tested.
  - **pytest comes from the calling environment**, since the suite runs as `sys.executable -m pytest`; it cannot come from the fixture campaign's venv, because the scenario's first act is `campaign init` and that campaign does not exist yet. So the documented invocation installs the `test` extra: `uvx --from 'git+https://github.com/con/mechababs@<ref>#egg=mechababs[test]' mechababs test-cluster --cluster <site.yaml> --scratch-path <scratch>`.
  - **The throwaway is a lone study, no superstudy** — the campaign-optional spine, which is also the first path an adopting lab walks. The full dev e2e suite covers both lone-study and superstudy scenarios; `test-cluster` runs only the lone-study one.
  - `test-cluster` fabricates the throwaway study (tiny sourcedata + per-subject TSV) — a test fixture, not study authoring re-entering scope.
  - Scenario touch-ups: the retire step supplies an outside-the-study target; the leave-it-clean check targets study cleanliness.
- **`mechababs campaign update-env` rebuilds the campaign venv from the committed lock.** Named `update-env` (not bare `update`) so it can't be confused with updating the campaign's *config*, which is a plain edit+commit. The verb for a fresh clone (lock present, no venv), for after a lock bump (the env-match guard's "now what"), and for rebuilding the env at a historical checkout during rerun-reproduction.
- **The configured-level check lives on `iterate`, not on `mechababs-inner`.** `iterate` enforces "operate a campaign only from where it was configured"; the inner action verbs carry only the cell-state self-guard. So `datalad rerun` of a recorded inner command (reproduction) just works, while user-driven advancing goes through `iterate` and is gated.
- **`iterate` reads only the study's own campaign config to enforce the configured level — it does not look outside the working directory.** When a campaign is super-configured, that fact is recorded in the **study's** campaign config (a superstudy-mode marker, written when the member's footprint is created at `add-dataset`). `iterate` run in the study reads that marker and refuses (operate from the super); it never scans parents to see if something claims ownership. `--force` overrides (advance a detached member anyway; the user owns the reconciliation).
- **`iterate` scope = the configured level; optional targets narrow within it.** From a study: advances that study's shard. From a superstudy: advances all member shards for the active campaign, or just one with `--study X`. `--derivative` narrows further, to the cells of one app config — at either level, and composable with `--study`. Run-location gives the level; the targets focus within it.
- **`retire-derivative` requires a target directory that must be outside the study, and moves the retired derivative there**, resetting the cell in the same transition (mechanics otherwise unchanged). No fixed in-study archive location; the command refuses a destination inside the study, so retired attempts never travel with a published study. At a superstudy, retire is still scoped to the member study whose cell it resets.
- **`status` renders tall as-is** — one row per cell, matching the statefile (no wide pivot). At a superstudy it is the computed rollup across member shards (no stored master).
- **`add-dataset` does not install a new source dataset into a study.** It selects a source dataset that is *already present* in the study; it does not bring raw data in. (This implementation; not ruled out later.)
- **One `add-dataset` command, no `add-study`.** Every add is "select a (study, source dataset) pair into the campaign"; the differences (study present vs not, lone study vs member) don't need separate commands. Cloning an existing study in as a member is not authoring, so it folds into `add-dataset`.
- **`add-dataset` runs from the campaign root, like every operating verb.** The study is the current directory (`require_study_root`), and `--sourcedata <path>` is a path **inside it** — resolved study-relative, refused if outside, absent, or not a directory. There is no locator machinery: where you stand is the study. (An earlier walk-up-from-the-path design was dropped as an over-generalization.)
- **At a superstudy, `add-dataset --study` names the member and `--sourcedata` is relative to it.** The verb still runs from the campaign root, which at a super is the superstudy — so reaching a member takes a second coordinate rather than a different place to stand: `--study <member>` selects the member (a path relative to the super), and `--sourcedata` re-bases onto that member instead of the cwd. Absent `--study`, everything is the lone-study behaviour unchanged. The configured-level rule is **enforced, not merely accommodated**, and in both directions: `--study` is accepted only for a super-configured campaign (passing it to a study-configured one is refused — there is no member to name), and `add-dataset` run inside a member study for a super-configured campaign refuses via the same superstudy-mode marker `iterate` reads, pointing the user at the super. Neither level can reach a campaign that belongs to the other. The alternative — `cd` into the member and let the command walk up to find the super — was rejected: it operates a super-configured campaign from inside a member, which is exactly the drift the configured-level rule exists to prevent, and it would make the super's catalog update a side effect of a command run somewhere else. It also would not have saved a second command shape, since a member that is not cloned yet gives nothing to stand in.
- **`--study` accepts a URL, and that is the one case where a selection verb brings something in.** A member that is not in the superstudy yet is cloned as a subdataset first, then selected. This is a deliberate, narrow exception to "add-dataset does not install data": the prohibition is about *source datasets* — the raw BIDS data a study must already hold — whereas a member study is the container that will hold them, and requiring a separate manual `datalad clone` before every first selection would be ceremony with no decision in it. Source data is still never fetched. Under a superstudy the verb additionally updates the super's committed membership catalog and writes the member's campaign footprint on first selection, per the fan-out entry in the campaign-definition section.
- **What `add-dataset` does: sniff + add-state-entry, not inclusion.** Sniff = verify the sourcedata exists in the study and read its summary metadata (per-subject datatypes/counts) to fill the cell's identity columns. Add-state-entry = write the cells (this source dataset × the campaign's apps, with `depends_on`) into the enclosing study's statefile shard, empty and unscaffolded, for the active campaign. The subject inclusion list is generated later, at scaffold time — not here.
  - **The sniff matches on `source_id` only when the study describes more than one source dataset.** A study's metadata TSV covers every source dataset in it, keyed by `source_id`. With several, the sourcedata directory's name selects among them (an unmatched name is refused, naming the ids that *are* described). With one — or with no `source_id` column at all — every row is that dataset's, which is what lets a generic slot (`sourcedata/raw`, whose directory name is not a dataset id) work.
  - **The app bundle is fixed at `campaign init`; a dataset is selected whole or not at all.** Re-adding a dataset that has any cell in the shard refuses — nothing is rewritten, nothing duplicated. Growing a running campaign's bundle is deliberately unsupported (con/mechababs#116): a campaign is a config epoch, so more apps means a new campaign.

## Provenance (`prov/`)

- **The BEP028 `prov/` record is out of scope for this rewrite.** It stays tracked separately (see [output_structure.md](output_structure.md)). The `datalad run` command capture above is the provenance this rewrite delivers.

## Non-goals / out of scope

- **mechababs never pushes to a remote and never removes or drops data.** Publishing and space reclamation are the user's acts, on their timing and credentials; mechababs produces the objects, reports they are finished, and *tolerates* the result (a pushed-and-uninstalled study, dropped content) as normal state, never as something to repair. (The babs-internal RIA pushes during a run are not an exception — machinery internal to the derivative, not publishing.) See [use_cases.md](use_cases.md) "Out of scope".
- **Roundup of out-of-scope calls made inline above:** a PyPI release (con/mechababs#113); the BEP028 `prov/` record; a priority mechanism beyond default order + `iterate --study`; concurrent operation within one campaign (blocked on babs RIA non-relocatability); study authoring (recommend a tool, don't build one); a `--campaign` flag (env var only).
- **A source dataset gaining subjects or sessions after scaffold — deferred in this implementation.** The inclusion is fixed at scaffold and babs fixes the job universe at init, so an already-scaffolded cell does not pick up new subjects. Deferred in the spec, not in the user stories — the [use_cases.md](use_cases.md) story stands as a requirement for later.
