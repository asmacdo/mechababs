# mechababs — requirements spec

The design decisions of record.
[use_cases.md](use_cases.md) holds the user stories these answer to; [output_structure.md](output_structure.md) holds the resulting layout; this document holds the requirements and the reasoning behind them.
Each entry should trace to a use case.

The spec is a contract for implementation, not gospel.
If a requirement forces the implementation somewhere weird, inefficient, or sloppy, the requirement is revisited — loudly, with options — rather than followed blindly.
Entries marked **Open** are named holes we have not decided.

## Installer & environment

- **No global install; no separate bootstrap verb.** The first command is `uvx mechababs campaign init …` — run ephemerally via uvx (nothing on PATH), it creates the first campaign *and* installs the venv. There is no standalone `bootstrap` step.
- **`campaign init --superstudy <name>` scaffolds a new superstudy** and creates the campaign at that level.
- **Init is scaffold-or-adopt, and never clobbers. It may create a superstudy, but it does not scaffold input studies.** Authoring input studies belongs to another tool (see "Layout & input"), and `-d` requires a dataset that is already there. A superstudy typically holds no raw data of its own. For mechababs, it should be treated as the coordinating container for member studies. `--superstudy NAME` scaffolds one when the name is not there yet. The cases, decided by what is at the target path: *nothing there* → create the datalad dataset (superstudy only; a study refuses), then scaffold `.mechababs/` and the campaign inside it. *Already a datalad dataset* → scaffold `.mechababs/` at its root; the directory may already carry campaigns, and an existing one is never modified. *A non-empty directory that is not a dataset* → refuse, rather than convert what is already there. *A campaign with this label already exists* → refuse, naming it. So a superstudy that has run campaigns before gains another by the same command that creates one from scratch, and adopting an existing dataset is the normal path rather than a special mode.
- **`campaign init` names its target with `-d`, mirroring datalad; every other verb runs from the root of the correct dataset.** `campaign init -d .` or `-d <path>` says which dataset to create the campaign in, the way `datalad -d` does, so the one verb that has to act on a dataset you may not be standing in says so explicitly. `--superstudy <name>` is the superstudy's counterpart and names the superstudy itself — created if that name is not there yet, adopted if it is. The superstudy is **not** the campaign and outlives it: one superstudy accumulates many campaigns over time, each with its own label, configs and lock, so the two are named separately and neither is derivable from the other. The other outer mechababs commands (`add-dataset`, `iterate`, `status`, `retire-derivative`) take no such flag: they run from the root of the dataset that owns the campaign — the superstudy for a super-configured campaign, the study for a study-configured one. That is what makes "operate a campaign only from the level it was configured" checkable rather than conventional, and it is why a superstudy-level `add-dataset` reaches a member with a `--study` selector instead of a different place to stand.
- **The uvx source can be a git ref or (future) PyPI.** This implementation uses a git ref (`uvx --from git+…@<ref> mechababs campaign init …`); a PyPI release gives the cleaner `uvx mechababs campaign init …` later. Publishing to PyPI is out of scope here (tracked by con/mechababs#113), but the design must not preclude it.
- **Once a campaign exists, mechababs runs from the installed venv** — uvx is only the first-campaign step; subsequent `campaign init` / `iterate` / … run from the venv.
- **One venv per campaign.** A campaign is one lock = one venv, pinning `mechababs` *and* `babs` together. The campaign is selected by label, so the CLI resolves the venv — the user never passes a project path.
- **Activate from the top level, then work.** The user activates the campaign's venv from the **superstudy if one exists, else the study**, and works from there. For a super-configured campaign, a member study carries no operational venv — outer mechababs commands at a member refuse, with no override. A venv can still be rebuilt from the member's committed lock (`uv sync`) for detached **reproduction**: `datalad rerun` of the member's recorded commands, with the user responsible for the environment they built. A member may also define study-level campaigns of its own (distinct labels; venv at the study, normal lone-study rules), but a member's own campaign and a super-campaign covering that member are **not run at the same time** — the member directory is shared state. The venvs themselves are gitignored and ephemeral, so nothing committed conflicts.
- **Each study carries the campaign lock (`.mechababs/campaigns/<label>/uv.lock`), committed — the study's own orchestration-provenance record, not a dormant copy.** All orchestration provenance lives in the study, so the study is independently reproducible: `uv sync` the lock, `datalad rerun` the recorded commands. The operational venv lives at the configured level (super for a super-campaign, study for a study-campaign) — one active venv per campaign; the venv is gitignored, rebuilt from the lock.
- **The lock is mutable via git history — this is how a mid-sweep version bump works.** A bump edits and commits the lock (a new study commit); completed cells keep the commit/lock that produced them (never redone), while new and selectively-redone cells run at the bumped lock. The lock's evolution *is* its git history: a `datalad rerun` checks out the run's commit → `uv sync` that commit's lock → rebuilds the exact env → redoes. The campaign goes deliberately heterogeneous (some cells at the old version, some at the new), honestly recorded. At a superstudy the bump edits the **canonical lock at the super**; each member receives it via `campaign update-env --study <member>` (see the canonical-vs-mirror entry below), never by hand-editing a member's copy.
- **The cluster config may declare `env_constraints`, and `campaign init` folds them into the campaign's pyproject.** Which package versions a site can install is a cluster fact, not a campaign or app one: an old glibc (CentOS 7's 2.17 is still common on HPC) stops loading the newest manylinux wheels long before it stops running jobs, and uv then falls back to source builds the site's compiler cannot complete. So a cluster config carries a list of verbatim PEP 508 specifiers, emitted as uv `constraint-dependencies` — caps that apply to whatever the resolution already contains, never adding a dependency or pinning one the site does not use. mechababs does not interpret them; the semantics are uv's. Absent or empty means no constraints, so a modern cluster declares nothing. When the environment build still hits a package with no installable wheel, `campaign init` fails naming that package and pointing at `env_constraints`, rather than leaving a compiler error to be read.
- **The env-match guard is two checks, and mechababs keeps no environment metadata of its own.** Before mechababs operates: (1) **location** — this process runs the selected campaign's venv (`sys.prefix` is the venv at the configured level), which only mechababs can know; (2) **freshness** — that venv matches the campaign's lock, delegated entirely to `uv sync --check` against the real installed environment (so a hand-`pip install`ed package is caught, not just a moved lock). Refuse on either (bumped the lock but didn't rebuild the venv, drifted the venv by hand, or running some other environment), naming `campaign update-env` as the fix. The only environment artifacts are the two standard ones — the lock (what should be installed) and the venv (what is) — compared by the tool that owns them; `uv` is itself a campaign dependency, resolved from the venv like every other pinned binary, so the check needs nothing ambient.
- **Honest caveat:** standalone reproduction is faithful only for fully-pinned locks (release- or commit-pinned deps are content-fixed and rebuild identically); a dev/editable/branch source does not reproduce — the accepted cost of one-tool-two-modes.

## Layout & input

- **Input is an existing BIDS study.** mechababs operates on a study that already exists on disk (cloned, or authored by another tool); it does not create one in this implementation. Not ruled out later — see the study-authoring gap in [output_structure.md](output_structure.md).
- **The expected study input includes the per-subject metadata TSV** (per-subject `datatypes` / `t1w_num` / `bold_num`) that selection and the `add-dataset` sniff read to apply eligibility rules. For this implementation it is expected present, as OpenNeuroStudies provides. Generating it when absent is follow-up generalization work. Eligibility rules are unchanged.
- **The container dataset is an input, not something mechababs vendors.** An app config's `container.source` is handed to `babs init --container-ds` as-is when it is a URL (what a production config carries), and otherwise resolved as a filesystem path — a relative one against the **study root**, so a config can name a sibling checkout without committing an absolute path. There is no copy-into-the-campaign step: babs installs the container dataset into each derivative, the way it installs any input. This works against a container dataset in its own native layout (ReproNim/containers' `images/<collection>/<app>--<version>.sif`) because babs resolves the image from its datalad-containers registration rather than a fixed path — `PennLINC/babs#399`, which is why the pinned babs matters here.
- **Derivative naming carries the source-dataset id when the sourcedata is named, and always the campaign label.** A cell is (source dataset × app config) in one campaign, and the name carries each part that can differ: `<Tool>-<Ver>+<stage>` alone would collide when a study holds several source datasets, and a study accumulates campaigns, so without the label a new campaign could not produce the same cell until the previous campaign's derivative was retired. When the sourcedata uses a generic slot (`sourcedata/raw`, `sourcedata/rawbids`) no id is needed. So the derivative is `<Tool>-<Ver>+<stage>[+<id>]+<label>/` (e.g. `fMRIPrep-25.1.1+anat+ds000001+c1`), the label last so the upstream `<Tool>-<Ver>` prefix stays and the `+` chain reads app, then source, then campaign.

## Campaign definition

- **Campaign selection: always the env var.** The `MECHABABS_CAMPAIGN` env var names the `<label>`, and sourcing the campaign's `env.sh` is what sets it — no default-if-one shortcut, so one campaign and five behave identically. No `--campaign` flag in this implementation (not ruled out later). The `<label>` (the `.mechababs/campaigns/<label>/` dir name) is the identity; the env var is a selector, not identity; there is no stored "active" pointer.
- **`campaign init` scaffolds a per-campaign `env.sh`.** Sourcing it both activates that campaign's venv and exports `MECHABABS_CAMPAIGN=<label>` — one step that selects and activates, and (because there is one venv per campaign) the two cannot mismatch. A user-sourced script works where an auto-set env var would not: it sets the current shell, whereas a mechababs subprocess cannot export to its parent. `env.sh` is committed (the venv path is deterministic) and lives where the venv does — the superstudy if one exists, else the study. The env-match guard still backstops a hand-set `MECHABABS_CAMPAIGN` whose venv isn't active.
- **App configs are user-provided.** mechababs ships `examples/` as starters to copy and adapt — not an authoritative shipped library. The configs a campaign runs are the user's own; the ease story is reuse of those configs.
- **Cluster configs are user-provided too** — same rule. Cluster configs are site-specific and often private (real paths never belong in `examples/`); mechababs ships example clusters as starters only.
- **`campaign init` locates configs by path or URL** — app and cluster configs are given as paths or URLs and copied into `.mechababs/campaigns/<label>/` (`bids-app-configs/`, `clusters/`). Not bare names resolved against a magic directory.
- **Which source datasets a campaign acts on is an explicit selection, via a required `add-dataset` step — not at `campaign init`.** A study may hold many source datasets and a campaign may act on only some. `campaign init` defines the app bundle + cluster + env; `add-dataset` then selects which source datasets the campaign acts on, populating the cells. The statefile cells are (selected source datasets × apps).
- **At a superstudy, a member's campaign footprint is written at `add-dataset`, not `campaign init`.** `campaign init` at a superstudy touches only the superstudy's own campaign dir — no members are selected yet, so there is nothing to fan out to. When `add-dataset` first selects a source dataset in a member, it writes that member's `.mechababs/campaigns/<label>/` (config copy, `pyproject.toml` *and* lock — a complete uv project, so a detached rerun can rebuild the environment from the member alone — empty statefile shard, superstudy-mode marker). No `env.sh` and no venv: the operational environment lives at the configured level. A member added later gets its footprint the same way — the copy happens at selection time, so there is no separate catch-up step.
- **`depends_on` is a mechababs-owned declaration in the app config, separate from babs's input config.** Each bids-app config names its own `depends_on` (e.g. fmriprep-minimal → fmriprep-anat). It is **not** derived from babs's `input_datasets` — orchestration topology is mechababs's, run-wiring is babs's; coupling them would also miss dependencies that are never inputs (a QC gate). A "pipeline" is the connected component of the edge graph — a derived view, not a stored object. The design leaves room for a first-class pipeline/bundle object that owns the topology later, without reworking the config format.
- **`depends_on` carries no kind: it is ordering, and nothing else.** A bare producer stem, meaning exactly one thing — the dependent cell is not scaffolded until that producer's cell is merged. It wires nothing and mechababs reads nothing else off it.
  - **Wiring is `input_datasets`', solely.** Scaffold resolves an `input_datasets` entry that names a producer cell in the shard to that cell's merged output store, without consulting `depends_on` at all. A key naming no cell is an input from outside the campaign and keeps the `origin_url` the config gives it.
  - **The two are declared side by side, and that is deliberate.** An input-chained stage (fmriprep-minimal ← fmriprep-anat) names its producer twice — `depends_on` for ordering, `input_datasets` for wiring — because they answer different questions and are consumed by different tools. A QC gate (fmriprep ← mriqc) names it once, in `depends_on`: the producer must complete and its report matters, but its output is not an input.
  - **The gate does not act on the QC verdict.** It delays the dependent until the producer is merged; whether subjects passed, and subtracting failures from the downstream selection, stays the user's act (curating the selection), not a mechababs mechanism.
- **A config edit mid-campaign reaches only cells not yet `babs init`-ed.** App and cluster configs are mutable the way the lock is — edit and commit, with evolution read from git history (at a superstudy, dispatch reads the **member's** config copy, which may deliberately override the canonical one — edit it in the member; how a canonical-copy edit propagates to members is open, some explicit per-member act). A cell already scaffolded keeps its baked job scripts and is not rewritten; to apply the change there, retire + re-scaffold. Awkward but honest — the same babs-bakes-at-init asymmetry as today's interventions.

## Statefile & reconciler

- **The statefile is per-(study, campaign), tall, at `.mechababs/campaigns/<label>/sourcedata+derivatives.tsv`.** One row per (source dataset × app config) cell — a map of source datasets to derivatives, named after OpenNeuroStudies' `studies+derivatives.tsv` one level down. A BIDS-conventional TSV so other tools can read it.
- **Columns:**
  - identity (inputs, written at `add-dataset`, never overwritten): `source_dataset`, `app_config`, `processing_level` (sub vs sub+ses), `n_subjects` / `n_sessions`.
    `app_config` is the **campaign-relative config path** (`bids-app-configs/MRIQC-24.0.2.yaml`), the same identity `campaign.yaml`'s `apps:` list carries; the filename stem is only a derived, human-facing form (display, derivative naming). Internal — the user names configs only at `campaign init`, by full path or URL.
    `depends_on` is *declared* in an app config by the producer's stem (the natural name to write) and stored resolved to the producer's path, so both identity columns hold the same kind of thing.
    `source_dataset` is the sourcedata's **study-relative path** (`sourcedata/ds000001`), not a bare id: it is what the user named, it is what scaffold wires into babs, and it does not assume the sourcedata sits at `sourcedata/<id>`.
    When a derivative carries an `+<id>` part, the id is that path's last component — and the generic slots (`sourcedata/raw`, `sourcedata/rawbids`) carry none, per the naming rule in "Layout & input".
    `processing_level` is read from the metadata rows themselves — session-level exactly when they name real sessions — rather than from which of the two metadata filenames the study happens to use.
    `n_sessions` counts sessions across all subjects, and is blank rather than 0 for a subject-level dataset.
  - topology (derived from the app config): `depends_on` (the upstream `app_config`, or empty).
  - durable derived (reconciled each iterate): `babs` (the derivative path once scaffolded — empty = not started), `merged` (set once merged — empty = not yet).
  - State is read off these — `babs` empty → scaffold; `babs` set + `merged` empty → active; `merged` set → done. Volatile job status stays in babs (queried live), never a column.
- **The `depends_on` gate is a shard-local row lookup.** A cell with a `depends_on` is not scaffolded until its **producer cell is `merged`**, where the producer is the same `source_dataset`'s upstream-`app_config` row in the same shard. It cannot cross studies — not by an enforced check, but because the reconciler only ever looks within the shard it is reconciling. Same at both levels. Input wiring is a separate lookup on the same shard, driven by `input_datasets` (above).
- **The inclusion pin and `--limit` live in the campaign.** `--limit` (still needed for testing) is a `campaign init` option recorded in `campaign.yaml` — a campaign-level fact, canonical at the configured level and reaching members like the rest of the config. The requested subject list is pinned in the member's campaign footprint at `.mechababs/campaigns/<label>/inclusions/<sourcedata>_<app>.csv`, beside the statefile shard. Both halves of a cell's identity are paths, so neither is filename-safe as written: `<sourcedata>` is the whole study-relative path with `/` mapped to `-` (whole, so two source datasets whose directories share a basename cannot collide on one pin), and `<app>` is the config's filename stem. The name is constructed from the cell and never parsed back into one — written at scaffold time inside that cell's `datalad run`, so the pin (and its diff against babs's own `processing_inclusion.csv`, the check that catches a selected subject the data doesn't have) travels with the study. If a file already exists at the pin path when a cell scaffolds, it is used as-is and selection is skipped entirely — so hand-writing a one-row file there before the first iterate runs a one-subject smoke test of the full pipeline, the same affordance today's campaigns have.
- **`iterate` gates by noting, not blocking.** A dependent cell whose producer is not complete is not advanced, but this is not a halt: iterate records "waiting on producer" as the cell's visible state and moves on; the next iterate re-checks (level-triggered).
- **Change-making transitions are `datalad run`-captured action subcommands, not plain saves.** Each transition becomes a mechababs action verb; the ones that make changes are dispatched via `datalad run`, so the commit records the actual command verbatim instead of a hand-written save label. Only mutating actions are wrapped — a read-only or non-committing action (a status query; a submit that only sbatches and changes nothing tracked) needs no `datalad run`. This is mostly moving existing transition code into subcommands, not a rewrite.
  - **One change-making write stays outside `datalad run`: the superstudy's own campaign files.** The inner run is always dispatched at the study (`-d <study>`), so the super's membership catalog + coarse lifecycle updates cannot land inside it; they are committed at the super as plain saves. **One save per tick that moved git state in a member** — a scaffold or a merge, which moves the member's gitlink — taken before the next cell is attempted. So a super commit never spans two derivatives (two subdatasets whose provenance has nothing to do with each other), and an iterate that dies mid-member leaves the super exactly as far as the last success rather than holding a stale gitlink. A submit moves nothing in git and is recorded at neither level.
  - **Whether an action subcommand leaves its facts to the run or saves them itself is decided per subcommand, by what it makes datalad see.** The payoff of leaving them — one plain RUNCMD commit carrying message, content and record together — is only reachable when the command makes no commit datalad can see. **`mechababs-inner scaffold` reaches it and keeps leave-uncommitted.** **`mechababs-inner merge` cannot**: `babs merge` plus the pull-back move the derivative subdataset's HEAD, so datalad always takes its protective split and emits the content half under its hardcoded, generic `Remaining changes after command execution`. `merge` therefore **saves its own study-level facts (shard + gitlink) last**, under `record: <derivative> is now merged`; the generic aux commit then does not arise and both remaining commits say something. The run record still wraps the subcommand's own commit — the record embraces the content, which is the shape to preserve.
  - **Every save says what happened, not how much.** A save message names the tick it records — the cell and its transition — and the lifecycle change, if any, that followed from it; never a bare count of cells. A count is what a save site writes when it has been handed a number instead of the work, and it leaves the campaign's own history unreadable to the git-only reader the committed lifecycle exists for.
  - `iterate` itself is a plain coordinator, **not** wrapped in a `datalad run` — it dispatches one run per advancing cell, so there is no same-level nesting.
  - The run is at the **study level** (`-d <study>`), where the derivative and statefile live. At a superstudy, `iterate` dispatches per-member study-level runs — the run's `-d` is always the (lone or member) study.
  - **Mechanics:** the inner run is `datalad run --explicit -d .` with cwd inside the study. The cwd makes the recorded command study-relative (portable, re-executable records); `--explicit` with each verb's declared output paths (the derivative, the statefile, the inclusion pin) keeps the run from deep-walking `sourcedata/raw` — datalad's dirty gate and save discovery ignore all submodule-ignore config, so path scoping is the only route. Because `--explicit` captures only declared outputs, a **shallow clean check** (gitlink compare, no descent into submodule worktrees) is the loud backstop for stray side-writes: once at the top of an iterate, and again before each dispatch, at the study it is about to change. At a superstudy the top-level check covers the super's own tree and **excludes the members** — each is asked about separately, by a gitlink compare immediately before it is advanced, so nothing is checked twice, one member's drift stops that member rather than the whole fan-out, and the cost stays flat instead of growing with the number of members.
  - **The scaffold verb declares `.gitmodules` among its outputs.** Registering the new derivative commits the registration mid-command, and datalad's undeclared-committed-path guard (`datalad.run.dirty-committed=error`) would refuse the run; declaring `.gitmodules` satisfies the guard while keeping it armed for genuinely unexpected mid-command commits — chosen deliberately over muting it.
- **Two record homes: orchestration → study, compute → derivative.** `datalad run -d <study> <action>` records the **orchestration** in the study (the derivative is an *output subdataset* of that run — the study-level diff is "new/updated subdataset + statefile"). `datalad run -d <derivative> singularity …` (the babs job) records the **compute** in the derivative. Different `-d`, different dataset levels, no nesting conflict.
- **Ordering is unchanged — no priority mechanism in this implementation.** Advance in default order (at a superstudy, members in catalog order; within a shard, cells in row order), bounded by `--batch`, with `depends_on` the only hard constraint. `--batch N` means the same thing at either level — at most N ticks per iterate, full stop; a cell that is passed over is not a tick — so at a superstudy it is the *iterate's* budget rather than each member's, spent in catalog order. That is what makes catalog order a priority interface and not only an ordering: `--batch 5` advances the five most important cells in the superstudy, wherever they live. The overrides are `iterate --study` (concentrate on one member) and `--app` (narrow further, to one app's cells).
- **The single-writer unit is the study or superstudy, not the campaign: one lock per study or superstudy, at `.mechababs/.single-writer.flock`.** A study or superstudy **may carry multiple campaigns, which coexist within a single checkout, but they are prevented from operating at the same time**. Campaigns may sit side by side under `.mechababs/campaigns/`, on one branch, in one checkout, and a study accumulating them over time is the design. The lock is held for the whole of any mechababs command that mutates the git state.
  - **Merge-back is a results-consolidation, not a relocation of running machinery.** A campaign lives its whole operating life in its worktree (where the baked store paths are valid); the branch merges back only when the campaign — or the cells being consolidated — is finished, and the merged-back derivative's RIA machinery is dead on arrival, accepted exactly as in the multi-cluster merge. Never continue operating a campaign from the merged-back copy; a cell that needs redoing after consolidation is retire + re-scaffold under a live campaign.
- **Concurrent operation *within* a single campaign is deferred** (branch-per-execution + merge). The blocker is babs's non-relocatable RIA stores (below).
- **Multi-cluster = two same-config campaigns, results merged by hand.** No single campaign spans clusters; you run one campaign per cluster (same configs) and consolidate the outputs later, conflicts hand-resolved. This works because you consolidate **results** (the derivative data — portable in git/annex), not running machinery; the babs RIA going dead on the merge is acceptable (you don't re-run a consolidated result). mechababs builds no cross-cluster coordination in this implementation.
- **Caveat, upstream: babs project non-relocatability is the local-abspath RIA stores — treat it as a babs limitation, not a permanent mechababs assumption.** babs bakes absolute local RIA paths at init, so a project can't move. This is behind: the within-campaign concurrency deferral, `retire-derivative` producing a dead archive, and the multi-cluster / branch merge killing the RIA. It is likely to change — RIAs able to live on remotes, or replaced by remotes generally — and when it does, branch-per-execution, clean relocation, and cross-cluster stop paying the abspath tax. Don't over-design around today's local RIAs.
- **The "active" cell decision is unchanged from today's model.** For a cell with `babs` set and `merged` empty, read `babs status` counts and decide: not-all-submitted → submit; still in flight → skip; all ended in failure → flag (don't merge, stop); all done → merge.
- **A dangling `depends_on` fails at `add-dataset`.** When a dependent cell is added, `add-dataset` checks the producer cell is present in the shard and fails if absent — so the producer is added first. No auto-adding the producer chain; fail early instead. Should a shard nonetheless carry one (only reachable by hand-editing), the reconciler routes that cell as waiting — naming the missing producer — and advances the others rather than failing the iterate; scaffold still refuses the cell if something dispatches it anyway.
- **The super's campaign dir is canonical for seeding and for the environment; a member's footprint is the member's own after creation.** A member's `.mechababs/campaigns/<label>/` is written from the canonical copy when `add-dataset` first selects it — and a footprint already sitting at that label is **reused only if this superstudy owns it**, else refused: labels are short user-chosen words and a study accumulates campaigns by design, so a member can arrive carrying its own standalone campaign, or another superstudy's, under the same name, and adopting it would write our cells into that campaign's statefile and run configs nobody chose here. From then on `iterate` never auto-syncs it — a study may carry deliberate per-study config overrides, so a footprint is not a mirror to converge. The inner verb reads the **study's** copy, so the recorded run reads only in-study state and the study alone suffices for reproduction. A version bump is an edit+commit at the super plus `campaign update-env`; a member whose lock copy is still at the old epoch is then **refused by the inner verbs' env check** — the running venv no longer matches the study-local lock — until `campaign update-env --study <member>` refreshes that member's **lock copy only** as its own committed act. Moving a member's remaining work onto a new environment is a human acknowledgment, never automatic. How a canonical **config** change propagates to members is open — a blind copy would clobber per-member overrides, so it is some explicit per-member act, not decided here. Complete members are never advanced, so never rewritten — they keep the config/lock that finished them. The env-match guard at the super compares the venv to the canonical lock; the member's lock copy is the provenance record the inner verbs' check keeps true.
  - Faithful replay of a recorded run is the rewind discipline: rewind to the run's commit, rebuild the env from that commit's lock (`campaign update-env` at that checkout; at a member — which is never operated from — raw `uv sync --frozen` against the member's own campaign dir), then `datalad rerun --explicit` — rerun does not inherit the recorded run's explicit mode, though the recorded outputs are forwarded. A bare `datalad rerun` onto current HEAD reads today's config/lock, and the cell-state self-guard refuses the already-done cell — the desired loud failure. Caveat: `rerun --onto`/`--branch` are refused on git-annex adjusted branches, so on crippled filesystems campaigns *run* fine but the rewind-replay mechanic is unavailable; the replay route there is open.
- **The statefile always lives at a study; the superstudy has none.** A member study's campaign dir carries the `sourcedata+derivatives.tsv` (and a config copy); the superstudy's same-labeled campaign dir carries membership and no cell state. Identical for study-only (the one shard) and superstudy (N shards + rollup).
- **The superstudy commits membership + a coarse per-member lifecycle status; detailed per-cell state stays computed.** The split is by granularity and change-rate:
  - the committed catalog points to member studies and their statefiles, and carries a coarse lifecycle per catalog row — one row per (member study, source dataset) — reading `registered` / `active` / `merged`: `merged` once every cell for that source dataset is merged, `active` once any of them has a babs project, `registered` until then.
  - that lifecycle is **derived from the member's shard, not accumulated by the transitions**: recomputed on each tick that scaffolds or merges one of its cells, and committed only when the value changed. Value changes are rare (roughly twice per member) and cost no commit of their own — the write lands in the per-tick save that already records the moved gitlink. The terminal transition is itself an advance, so a member reaches `merged` on the tick that merges its last cell.
  - detailed per-cell state is computed on demand from the member shards (small git-tracked TSVs, cheaply fetchable even when derivative *content* isn't installed). It is not committed at the superstudy.
  - Store the coarse **view** (the per-row lifecycle) so a reader who cannot reach the member still has one; compute the detailed view (per-cell from shards) for a reader who can. The shard stays canonical for both, so the catalog is never a second source of truth to reconcile against.
  - One writer: a super-campaign is operated only from the super (the configured-level rule), so only the super updates its catalog and no standalone member action can stale it. **mechababs does not scan for drift and does not reconcile it away.** A tree that is dirty when an iterate begins stops the iterate (`require_clean_shallow`, `require_clean_gitlink`); it is not absorbed. Recomputing the lifecycle is how the value is produced, not a repair pass for edits made behind the tool.
  - **Open (noted gap, no machinery planned):** a crash between a member's terminal merge commit and the catalog write, followed by the user uninstalling the member before another iterate, leaves the lifecycle stale at `active` with nothing installed to recompute from. The suspected answer is documentation, not machinery: check a study is no longer active before removing it.
- **`iterate` handles a study that has left the cluster by leaving it alone.** iterate advances only **installed** members; a finished study the user pushed and uninstalled is not present, so iterate skips it and never reinstalls to advance it. A done study whose content was dropped but whose git remains: iterate reads its shard → all `merged` → skip (done cells need no content). No "done" marker is needed — reinstall it later and the shard drives it (state derived from ground truth). The user's uninstall is the level-triggered signal.
- **Superstudy observability.** The coarse per-member lifecycle lives in the committed catalog — it exists for off-cluster/git readers and is decoupled from `status`. `status` at the super is the computed rollup from member shards, plus installed-vs-not from local git; installed members drill into per-cell detail from their local shards, and an uninstalled member's per-cell detail requires fetching its shard (git, cheap, no content).
- **A campaign is operated only from the level it was configured.** A super-configured campaign is operated from the superstudy (optionally scoped to one member); a study-configured campaign is operated from the study. The same campaign is never operated cross-level. This gives each campaign exactly one operating level and eliminates the drift cross-level operation would cause: config copies edited in one member diverging from siblings; a tool bumped in one member so "one campaign, one lock" erodes; a member's standalone `add-dataset` creating a cell the super's catalog doesn't list; super and member advancing the same member concurrently; two levels both claiming to drive the same label. Version bumps for a super-campaign therefore happen at the super, applied uniformly — never from inside a member. (Benign gitlink drift — a member advances, the super's pinned pointer lags — remains, reconciled at publish.)
  - **Open disagreement to resolve:** the alternative model — after a campaign is configured at the super, a member operates *independently* on that super-campaign and the super *reconciles later*. This spec rejects it because reconciling arbitrary member divergence (config/env edits made standalone) is drift we can't bound; what the design offers instead — a member running its own study-level campaigns under distinct labels — is a different affordance, not a substitute. To be discussed.
  - **Open, related:** whether the coarse committed lifecycle satisfies the dashboard want for materialized state at the superstudy, or more must be committed. To be discussed.

## CLI surface

- **Two entrypoints (console_scripts).** `mechababs` is the user CLI (`campaign init`, `add-dataset`, `iterate`, `status`, `jobs`, `retire-derivative`, `campaign update-env`, `test-cluster`); `mechababs-inner` (working name) carries the action verbs (`scaffold` / `submit` / `merge`) that `iterate` dispatches — the change-making ones under `datalad run`. The inner verbs are hidden from users, self-labeling in run records (a runcmd is unambiguously a machine-dispatched provenance step), and self-guarding (refuse a cell not in the right state).
- **`test-cluster` recreates the environment it was called from, in a throwaway study.** The durable pieces (per con/mechababs#104): the command surface, the e2e suite shipped as package data (`importlib.resources`, chosen in con/mechababs#98 precisely because there is no clone to reach into), fail-loud fixtures, and the throwaway-workspace principle. There is no campaign to invoke it from: a campaign lives *inside* a study, so nothing standalone can be pointed at or stood in. It therefore runs from anywhere, taking a cluster config by path and a `--scratch-path` to work in — required, since there is no campaign to derive one from and RIA stores must not land in home or `/tmp`.
  - **The two pins reach the fixture campaign differently, and the asymmetry is intended.** *mechababs mirrors the caller*: with `--mechababs` unset, `campaign init` pins whichever mechababs is running it (PEP 610 install metadata), so the code validated is the code invoked — dev-exercises-prod, by the same path a user's own `campaign init` takes. *babs cannot mirror the caller*: babs is not a mechababs dependency, it is a dependency of the **generated campaign**, frozen by that campaign's lock — so the fixture campaign gets what a user's campaign would get. Both are overridable (`--mechababs URL@REF`, `--babs URL@REF`), which is how a branch gets tested.
  - **pytest comes from the calling environment**, since the suite runs as `sys.executable -m pytest`; it cannot come from the fixture campaign's venv, because the scenario's first act is `campaign init` and that campaign does not exist yet. So the documented invocation installs the `test` extra: `uvx --from 'git+https://github.com/con/mechababs@<ref>#egg=mechababs[test]' mechababs test-cluster --cluster <site.yaml> --scratch-path <scratch>`.
  - `test-cluster` fabricates the throwaway study (tiny sourcedata + per-subject TSV) — a test fixture, not study authoring re-entering scope.
- **`mechababs campaign update-env` converges the environment on the declaration** — `uv lock` + `uv sync --frozen` + a scoped `datalad save` of `pyproject.toml` and `uv.lock` when they changed (a plain save, not a `datalad run`: `uv lock` resolves against the live world, so recording it as a re-executable command would be a false promise — the lock file itself is the reproducible artifact). Its behavior follows from the pyproject's state: untouched → the lock does not move and the venv is rebuilt from it (a fresh clone, a wiped site, after a passive `git pull`, a historical checkout during rerun-reproduction — and a *branch* pin already locked is never chased to its tip by a bare re-lock); edited → the changed declaration re-resolves and installs (the deliberate bump — the env-match guard's "now what"). Named `update-env` (not bare `update`) so it can't be confused with updating the campaign's *config*, which is a plain edit+commit. Two flags: `--upgrade <pkg>` (repeatable) passes `uv lock --upgrade-package <pkg>` — the one case with nothing to edit, a pinned branch whose tip moved; it touches only the lock, never the pyproject (the pyproject declares intent, the lock records resolution). `--study <member>`, at a superstudy, additionally copies the resulting canonical lock into that member's footprint as its own committed act (see the canonical-vs-mirror entry). It is exempt from the env-match guard the way `campaign init` is — its job is to run exactly when the guard fails or the venv is absent — but it is still an outer mechababs command: run it at the configured level, never at a member.
- **The configured-level and location checks live on the outer mechababs commands, not on `mechababs-inner`.** The outer commands (`iterate`, `add-dataset`, `status`) enforce "operate a campaign only from where it was configured" and that this process runs the campaign's own venv. The inner action verbs carry the cell-state self-guard plus one delegated environment check — `uv sync --check` of the **running** venv against the **study-local** lock — because a recorded inner command has a second entry path that never passes through an outer command: `datalad rerun` executes it directly, so the command must validate its own environment wherever it is replayed. A rerun therefore just works in any venv built from the study's committed lock, wherever the study sits, while an env that contradicts that lock is refused rather than misattributed — and on the dispatched path (where the outer guard already proved venv = canonical lock) the same check is what refuses a member whose lock copy is behind. User-driven advancing still goes through `iterate` and is gated.
- **`iterate` reads only the study's own campaign config to enforce the configured level — it does not look outside the working directory.** When a campaign is super-configured, that fact is recorded in the **study's** campaign config: the superstudy's **datalad-id**, written when the member's footprint is created at `add-dataset`. An id rather than a path, because a path re-resolves against wherever the member currently sits and would silently adopt whatever is above it. `iterate` run in the study reads that marker and refuses (operate from the super); it never scans parents to see if something claims ownership. Resolving that id back to a *place* walks up from the member, but only while operating at the superstudy — so the walk stays inside the directory the command is running in, and a member has already named its owner, so no other ancestor can change the answer. There is no override: a member is not operated from, even detached — a member detached from its superstudy supports reproduction (`datalad rerun`), not advancing.
- **`iterate` scope = the configured level; optional targets narrow within it.** From a study: advances that study's shard. From a superstudy: advances all member shards for the active campaign, or just one with `--study X`. `--app` narrows further, to the cells of one app config — at either level, and composable with `--study`. Run-location gives the level; the targets focus within it.
- **`retire-derivative <derivative-path> (--remove | --path DEST)` — the destination is a required choice, and there is no in-tree archive.** `babs init` refuses an existing path, so a cell that has to be redone cannot be re-scaffolded until its derivative leaves. Where it goes is exactly one of two flags, mutually exclusive and neither defaulted, because keeping the evidence and throwing it away are different decisions and neither is safe to make on the user's behalf. `--path DEST` archives it at `DEST/<study>-<derivative>-attempt-<N>` (first free N, never clobbers; the study name is the prefix so one DEST can collect attempts from several studies, and the source-dataset id already rides in the derivative name). **DEST must resolve outside the study — and outside the whole superstudy, when the campaign is operated at one** — checked on the resolved path, so a `..` or a symlink reaching back in is refused: a study is a published object we may not own, and a retired attempt inside it would travel with it. There is **no fixed in-study archive location**; the old campaign-owned `derivative-attempts/` belonged to the campaign-as-dataset shape and is gone. `--remove` deletes the derivative outright, for a cell whose evidence is worth nothing (a disposable test campaign, a scaffold that failed before any job ran).
  - **The cell is reset in the same transition**, so there is no window where the derivative is gone but the reconciler still routes it as in-progress. Only the derived columns are blanked; identity and topology are untouched — the cell is not being unselected, it is going back to the start of its own life, and membership at a superstudy does not change either. The cell is found by matching the `babs` column scaffold wrote (the campaign's own claim on that derivative), and a derivative no cell claims is refused *before* anything moves.
  - **Every level commits its own facts.** At a lone study that is one commit: the deregistered subdataset, the `.gitmodules` entry, and the shard row. At a superstudy retire is still scoped to the member study whose cell it resets — the member commits those three, and the super commits the one thing only it can see, the member's moved gitlink.
  - **A plain scoped save, not a `datalad run`.** Recording retire as re-executable would be a false promise in both modes: `--remove` destroys content, so a rerun onto a re-scaffolded cell would delete a *different* derivative, and `--path` names a host directory outside every dataset, which does not resolve elsewhere. Same argument as `campaign update-env` — it is a human intervention, not a reconciler transition.
- **`status` renders tall as-is** — one row per cell, matching the statefile (no wide pivot). At a superstudy it is the computed rollup across member shards (no stored master).
- **`jobs` is the drill-down under `status`'s cells** — one row per job babs is tracking, tagged with the study, source dataset and app it belongs to, and where its log is. Read-only and lock-free, like `status`.
- **`add-dataset` does not install a new source dataset into a study.** It selects a source dataset that is *already present* in the study; it does not bring raw data in. (This implementation; not ruled out later.)
- **One `add-dataset` command, no `add-study`.** Every add is "select a (study, source dataset) pair into the campaign"; the differences (study present vs not, lone study vs member) don't need separate commands. Cloning an existing study in as a member is not authoring, so it folds into `add-dataset`.
- **`add-dataset` runs from the campaign root, like every outer mechababs command.** The study is the current directory (`require_study_root`), and `--sourcedata <path>` is a path **inside it** — resolved study-relative, refused if outside, absent, or not a directory. There is no locator machinery: where you stand is the study. (An earlier walk-up-from-the-path design was dropped as an over-generalization.)
- **At a superstudy, `add-dataset --study` names the member and `--sourcedata` is relative to it.** The verb still runs from the campaign root, which at a super is the superstudy — so reaching a member takes a second coordinate rather than a different place to stand: `--study <member>` selects the member (a path relative to the super), and `--sourcedata` re-bases onto that member instead of the cwd. At a superstudy `--study` is required — omitting it is refused, naming what to pass — while a study-configured campaign has no member to name and `--sourcedata` alone is the whole of it. The configured-level rule is **enforced, not merely accommodated**, and in both directions: `--study` is accepted only for a super-configured campaign (passing it to a study-configured one is refused — there is no member to name), and `add-dataset` run inside a member study for a super-configured campaign refuses via the same superstudy-mode marker `iterate` reads, pointing the user at the super. Neither level can reach a campaign that belongs to the other. The alternative — `cd` into the member and let the command walk up to find the super — was rejected: it operates a super-configured campaign from inside a member, which is exactly the drift the configured-level rule exists to prevent, and it would make the super's catalog update a side effect of a command run somewhere else. It also would not have saved a second command shape, since a member that is not cloned yet gives nothing to stand in.
- **`--study` accepts a URL, and that is the one case where a selection verb brings something in.** A member that is not in the superstudy yet is cloned as a subdataset first, then selected. This is a deliberate, narrow exception to "add-dataset does not install data": the prohibition is about *source datasets* — the raw BIDS data a study must already hold — whereas a member study is the container that will hold them, and requiring a separate manual `datalad clone` before every first selection would be ceremony with no decision in it. Source data is still never fetched. Under a superstudy the verb additionally updates the super's committed membership catalog and writes the member's campaign footprint on first selection, per the fan-out entry in the campaign-definition section.
- **What `add-dataset` does: sniff + add-state-entry, not inclusion.** Sniff = verify the sourcedata exists in the study and read its summary metadata (per-subject datatypes/counts) to fill the cell's identity columns. Add-state-entry = write the cells (this source dataset × the campaign's apps, with `depends_on`) into the enclosing study's statefile shard, empty and unscaffolded, for the active campaign. The subject inclusion list is generated later, at scaffold time — not here.
  - **The sniff matches on `source_id` only when the study describes more than one source dataset.** A study's metadata TSV covers every source dataset in it, keyed by `source_id`. With several, the sourcedata directory's name selects among them (an unmatched name is refused, naming the ids that *are* described). With one — or with no `source_id` column at all — every row is that dataset's, which is what lets a generic slot (`sourcedata/raw`, whose directory name is not a dataset id) work.
  - **The app bundle is fixed at `campaign init`; a dataset is selected whole or not at all.** Re-adding a dataset that has any cell in the shard refuses — nothing is rewritten, nothing duplicated. Growing a running campaign's bundle is deliberately unsupported (con/mechababs#116): a campaign's bundle and lock are fixed, so more apps means a new campaign.

## Non-goals / out of scope

- **mechababs never pushes to a remote and never removes or drops data.** Publishing and space reclamation are the user's acts, on their timing and credentials; mechababs produces the objects, reports they are finished, and *tolerates* the result (a pushed-and-uninstalled study, dropped content) as normal state, never as something to repair. (The babs-internal RIA pushes during a run are not an exception — machinery internal to the derivative, not publishing. Neither is `retire-derivative --remove`: it deletes one named derivative because the user said to, with no default and no path by which mechababs reaches that decision on its own. What the non-goal rules out is mechababs deciding *for* you that something is no longer needed.) See [use_cases.md](use_cases.md) "Out of scope".
- **Roundup of out-of-scope calls made inline above:** a PyPI release (con/mechababs#113); the BEP028 `prov/` record; a priority mechanism beyond default order + `iterate --study`; concurrent operation within one campaign (blocked on babs RIA non-relocatability); study authoring (recommend a tool, don't build one); a `--campaign` flag (env var only).
- **A source dataset gaining subjects or sessions after scaffold — deferred.** The inclusion is fixed at scaffold and babs fixes the job universe at init, so an already-scaffolded cell does not pick up new subjects. Deferred in the spec, not in the user stories — the [use_cases.md](use_cases.md) story stands as a requirement for later.
